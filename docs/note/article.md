# 「あれ、日本語になってない」を2度押しで救うMacアプリを作って、App Storeに2回蹴られた話

## sonocheckma-kuhadokomadegahannidesuka

Macで日本語を打っていると、たまにこうなります。

```
sonocheckma-kuhadokomadegahannidesuka
```

「そのcheckマークはどこまでが範囲ですか」と打ったつもりが、英数モードのままだった。
37文字ぜんぶローマ字。気づくのはいつも打ち終わったあとです。

やることは決まっています。全部消して、かなキーを押して、もう一度同じことを打つ。
1回15秒として、1日5回で75秒。1年で7時間半。

この「消して、切り替えて、打ち直す」を肩代わりするアプリを作りました。
**I think so** という名前です。

---

## 何をするアプリか

メニューバーに常駐して、直前に打った文字列を覚えています。

打ち間違えたら、**行きたいモードのキーを2回押す**。それだけです。

《ここに table.png を挿入》

かな（または右⌘）を2回で、日本語に。
英数（または左⌘）を2回で、英語に。

JIS配列では、スペースキーの右が「かな」、左が「英数」です。
**「かなにしたい」なら右、「英数にしたい」なら左**。押すキーと行き先が一致します。

US配列やMacBookで「かな/英数」がなくても、左右のコマンドキーで同じことができます。

### 英単語は英単語のまま残る

さきほどの例で、`check` の部分だけ英語のまま残っているのに気づいたでしょうか。

```
sonocheckma-kuhadokomadegahannidesuka
　　↓ かな×2
そのcheckマークはどこまでが範囲ですか
```

全部を機械的にかなへ流すと「そのちぇckまーく」のような結果になります。
そこで約400語の英単語辞書を持たせて、文中の英単語を切り出し、
そこだけ英字のまま流し込んでいます。

### ローマ字のタイポも直す

```
sonotuskiwomita  →  その月を見た
```

`tsuki` と打つつもりが `tuski`。`sk` はローマ字として成立しないので、
「ここで読めなくなった」と分かります。転置・余分な文字の削除・
キーボードの隣のキーとの置換を順に試して、読める綴りに直します。

`checj`（`k` のつもりで `j`）のような英単語のタイポも、辞書と照らして直します。

**ただし直せないものもあります。** `si`（し）を `so`（そ）と打った場合、
`so` はローマ字として完全に正しいので、そもそも異常だと気づけません。
これを直すには「そのかなが日本語として自然か」を判定する必要があります。
後述しますが、ここには手を出さないことにしました。

## 作ってみて分かった、macOSの意外な仕様

ここからは技術寄りの話です。作る前は「1週間くらいかな」と思っていました。
実際は3週間、53コミットかかりました。理由はだいたいこの3つです。

### 1. 入力ソースは、APIで切り替えても前面アプリに効かない

macOSには `TISSelectInputSource` という入力ソース切り替えAPIがあります。
これを呼べば日本語モードに変わる、と思うじゃないですか。

**変わりません。**正確には、自分のプロセスの中では変わりますが、
いま入力を受けている前面のアプリには何の影響もありません。
バックグラウンドのメニューバーアプリから呼んでも、TextEditは英数のままです。

結局どうしたかというと、**「かな」キーそのものを押したことにしています。**
キーコード104のキーイベントを合成して投げる。原始的ですが、これが確実です。

同じ理由で「いま日本語モードか英語モードか」も取得できません。
`TISCopyCurrentKeyboardInputSource` は自分のプロセスの状態を返すだけです。
最初は「現在のモードを見て方向を自動判定する」設計にしていたのですが、
実機では毎回外れました。**方向の自動判定は諦めて、押すキーで明示する設計に変えました。**
結果的にこれが分かりやすくてよかったです。

### 2. ライブ変換は、読めない綴りが1つあると全部あきらめる

macOSのことえりには「ライブ変換」があります。打つそばから漢字に変わるあれです。

ここに `sonocheckma-kuhado...` をそのまま流し込むと、どうなるか。
`check` の `ck` あたりで解釈に失敗して、**それまで変換していた分を含めて、
文字列全体が生のアルファベットに戻ります。**部分的に諦めるのではなく、全面撤退します。

なので、流し込む前にこちらで日本語区間と英語区間に切り分けて、
日本語区間はキーコードで打鍵、英語区間は文字を直接流し込む、と
別々の方法で注入しています。区間の境目では変換を確定させてから次に進みます。

### 3. 日本語IMEが有効なままだと、BackSpaceが消える

これが一番てこずりました。

打ち直しの手順は「消す → 日本語モードにする → 打ち直す」です。
素直に実装すると、12文字消すためにBackSpaceを12回送ります。

ところが結果がこうなる。

```
aikososubete → かな×2 → aik愛こそ全て
```

`愛こそ全て` への変換は完璧なのに、`aik` が消え残っています。
しかも**毎回残る数が違う**（3文字だったり5文字だったり）。

送出が速すぎるのかと思って、間隔を12ミリ秒から30ミリ秒に広げました。**変わりません。**

ログを仕込んで分かったのは、
アプリは12回きっちり送っていて、自分のイベントタップは1つも飲んでいない、ということ。
つまり犯人はもっと外側、**ことえり**でした。

日本語IMEが有効な状態でキーイベントを送ると、すべてIMEを経由します。
未確定の文字がなくても経由します。そしてIMEは、送られたBackSpaceを不定個数飲みます。

直し方はシンプルでした。**順番を変えます。**

```
（変更前）日本語モードにする → 消す → 打ち直す
（変更後）英数モードにする → 消す → 日本語モードにする → 打ち直す
```

消す作業をIMEの外に追い出しただけです。
これで取りこぼしはゼロになり、しかも間隔を12ミリ秒に戻しても落ちなくなりました。
遅かったのではなく、通る道が悪かったということです。

### おまけ: イベントタップは、OSに止められると自力で戻らない

「朝は動いていたのに、気づいたら反応しない」という現象がありました。
アプリは生きていて、メニューバーにもいるのに、キーが届かない。

macOSは、コールバックが遅れたときやスリープ復帰時に、
イベントタップを一方的に無効化することがあります。
そのときタップには通常のキーではなく `.tapDisabledByTimeout` が流れてきます。
これを無視していると、**タップは止まったまま二度と戻りません。**

```swift
if type == .tapDisabledByTimeout || type == .tapDisabledByUserInput {
    if let tap = eventTap { CGEvent.tapEnable(tap: tap, enable: true) }
    return Unmanaged.passRetained(event)
}
```

3行です。CGEventTapを使うなら、これは必ず書いてください。

## App Storeには出せませんでした

作ったからには公開しよう、とMac App Storeに申請しました。結果は却下2回です。

**1回目**は Guideline 2.1、「情報が足りない」という定型の要求でした。
画面収録と7項目の説明を出せ、というもの。これは録画を撮って返信したら通りました。

**2回目**が本丸です。**Guideline 2.4.5。**

> アクセシビリティ機能を、アクセシビリティ以外の目的に使ってはいけない

このアプリはキーイベントを送出するために、システム設定で
「アクセシビリティ」と表示される許可を求めます。それが引っかかりました。

こちらの言い分はこうです。**このアプリはアクセシビリティAPIを一切呼んでいません。**
`AXUIElement` も `AXIsProcessTrusted` も使っていない。
提出したバイナリに `nm -u` をかければ、AX系のシンボルが1つも出てこないことは確認できます。

使っているのは `CGEventPost` で、これを管理しているのは
`kTCCServicePostEvent` という別のサービスです。
macOSがその同意画面を「アクセシビリティ」のペインに置いているだけで、
能力としては「キーイベントを送る」であって「アクセシビリティAPIで画面を読む」ではありません。

そう返信しました。返ってきた答えがこれです。

> `NSEvent.addLocalMonitor` を使ってください

`addLocalMonitor` は**自分のアプリのウィンドウに届いたイベントしか見えません。**
このアプリが読む必要があるのは、ユーザーがTextEditやブラウザに打った文字です。
ローカルモニタでは1文字も取れません。

`addGlobalMonitor` なら他アプリのイベントも見えますが、
こちらは**イベントを止められない**ので、トリガーのキーが前面アプリに漏れます。
そもそも打ち直しの注入ができません。

つまり、提案されたどちらのAPIでも、この製品は成立しません。
その旨を返信して、いまも回答待ちです。

もっとも、見通しは持っています。キー入力を注入する系のユーティリティが
軒並みMac App Storeの外で配布されているのは、この壁が動かないからでしょう。

### なので、自分のサイトから配ることにしました

Developer ID で署名して、Appleの公証（notarization）を通せば、
App Store の外でも警告なしにインストールできるアプリになります。

ここで1つ罠がありました。公証に出したら弾かれたのです。

> The executable requests the com.apple.security.get-task-allow entitlement.

`get-task-allow` はデバッガ接続を許す設定です。空のentitlementsを指定したのに、
**Xcodeが署名時に勝手に注入していました。**止めるにはこれを指定します。

```
CODE_SIGN_INJECT_BASE_ENTITLEMENTS=NO
```

これで通りました。ちなみに公証は、ビルドに使ったマシンのOSバージョンを見ません。
ベータ版のmacOSで作ったものでも通ります（App Storeへのアップロードは弾かれます）。

## 直さないと決めたこと

冒頭で触れた「`si` を `so` と打ってしまう」問題です。

`そ` は正しいかななので、文字列だけ見ても異常は分かりません。
判定するには「日本語として自然か」を見る必要があります。

macOSの自然言語解析で、かなを形態素に分けて採点する方法を試しました。
おかしな綴りは細かく刻まれるはず、という発想です。

```
正 しつもん → 1形態素 ["しつもん"]
誤 そつもん → 2形態素 ["そつ", "もん"]      ちゃんと判別できる
```

いけそうに見えました。ところがこういう例が出ます。

```
正 これがてすと → 5形態素 ["これ","が","て","す","と"]
誤 これがてそと → 4形態素 ["これ","が","て","そと"]   逆転
```

**正しく打った文のほうが不自然だと判定されました。**「そと（外）」が実在の語だからです。

この方式を入れると、正しく打った文字を勝手に壊します。
直らないより明確に悪い。**実装しない判断をしました。**

漢字のないかなの列は多義的すぎて、この判定は原理的に安定しません。
安全にやるには本格的な形態素辞書と文脈モデルが要ります。

## 使ってみてください

- **ダウンロード**: https://ithinkso.gigowat.com/
- macOS 13以降 / 約1.3MB / 無料
- Apple公証済み。開いてApplicationsにドラッグするだけです

初回起動時に「入力監視」と「アクセシビリティ」の許可を求めます。
どちらも中核機能に必要です。
**許可したあとはアプリの再起動が必要**です（許可しただけでは反映されません）。

打った内容はメモリ上の一時バッファでのみ扱います。
ディスクに保存せず、外部にも送りません。そもそもネットワーク通信の機能がありません。
スペースやEnter、修飾キーを押すたびにバッファは捨てられます。

## おわりに

3週間で53コミット。当初の見積もりの3倍かかりました。

時間を食ったのは、アルゴリズムではなく**環境の仕様**でした。
入力ソースは切り替えられない、ライブ変換は全面撤退する、
IMEはBackSpaceを飲む。どれもドキュメントには書いていません。
ログを仕込んで、1つずつ潰していくしかありませんでした。

一番の教訓は、**推測でパラメータをいじらないこと**です。
BackSpaceが消える問題で、私は最初「送出が速いのだろう」と決めつけて
間隔を2.5倍にしました。何も変わりませんでした。
ログを見たら、送出は完璧で、通り道が間違っていただけでした。

キーを変える前に、まずログを見る。だいたいこれで解決します。
